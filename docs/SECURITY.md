# Security

How Before You Tape uses Firebase AI Logic safely, row by row against Firebase's own
[AI Logic security checklist](https://firebase.google.com/docs/ai-logic/security-checklist), with the
date each row was read back and how anyone can check it. States: VERIFIED (read back, with evidence),
PENDING (with its plan and date), DECIDED-NO (with the reason).

Project: `before-you-tape-2026`. Backend: the Gemini Developer API (`GoogleAIBackend` in
`src/firebase/app.ts`).

## Check it yourself

A call to Firebase AI Logic with the site's public web key but no App Check token is refused, so no
model ever answers it. The key ships in every page, so take it from the site itself:

```bash
JS=$(curl -s https://before-you-tape-2026.web.app/ | grep -o '/assets/index-[A-Za-z0-9_-]*\.js' | head -1)
KEY=$(curl -s "https://before-you-tape-2026.web.app$JS" | grep -o 'AIza[0-9A-Za-z_-]\{35\}' | head -1)
curl -s -X POST \
  "https://firebasevertexai.googleapis.com/v1beta/projects/before-you-tape-2026/models/gemini-3.5-flash-lite:generateContent" \
  -H "Content-Type: application/json" -H "x-goog-api-key: $KEY" -H "Referer: https://before-you-tape-2026.web.app/" \
  -d '{"contents":[{"role":"user","parts":[{"text":"Say ok."}]}]}'
```

Expected answer: HTTP 401 with `"message": "Firebase App Check token is invalid."` The daily probe
(`scripts/probe-live.ts`, run by `.github/workflows/probe-live.yml`) makes the same call and fails if the
answer is anything else.

## Cloud calls

Every cloud model call, all through Firebase AI Logic with App Check, all paused by `kill_cloud`:

| Call | Where | Prompt | Why |
|---|---|---|---|
| Item read, hybrid | `src/ai/itemRead.ts` (`PREFER_ON_DEVICE`) | the item-read prompt and the cropped photo | Used only when the device model is ready and cloud checks are allowed; the cloud answers only when the device model cannot |
| Item read, cloud only | `src/ai/itemRead.ts` (`ONLY_IN_CLOUD`) | the same | When the browser has no on-device model and the sender allowed cloud checks |
| Fallback model | `src/ai/itemRead.ts` | the same | One try on a second model after a 500 or 503 survives the retry, or a 404 says the model is gone |
| Second look | `src/ai/secondLook.ts` | the same crop and prompt | When the policy names a reason, after an on-device read |
| Product-text read | `src/bridge/main.ts`, through `createProductCloudPort` in `src/ai/firebaseModels.ts` (`ONLY_IN_CLOUD`) | the product text in the Chrome extension's panel, with the product-text system instruction | When the sender allowed cloud checks in the panel and pressed Read in the cloud. The call runs in this site's bridge page (`/ext-bridge.html`), so it uses this site's App Check and anonymous sign-in, and it reads `kill_cloud` before and after sign-in |

No page asks for customs-form descriptions yet. Their prompt (`describePrompt` in `src/ai/prompts.ts`) is written, but nothing calls it, so it makes no cloud call today. If a page starts to use it, that call is added to the table above. The cloud text model in `src/ai/firebaseModels.ts` (`createTextCloudModel`) is in use: it is the model behind the product-text read.

A cloud-only item read or second look that fails with a network error, a 429 or a 5xx is retried once, while cloud checks stay allowed (`src/ai/itemRead.ts`). A hybrid read whose device step fails may already have tried the cloud inside the SDK, then takes this same cloud-only path, so it can reach the cloud up to three times. The status is the SDK's own error field (`customErrorData.status`) whenever that field is set; only without it is the number in the error message read, with any URL taken out first. A "Failed to fetch" carries no status at all, so after its one retry the call fails as "cloud unreachable" and the fallback model is not tried: the fallback is only for a model that is overloaded (500 or 503) or gone (a 404 that says so). For a first read, the page then says the cloud check could not connect, and the sender can try again or type the item. A second look that fails this way keeps the device read and its verdict, says on the card that there is no connection, and runs again the next time the browser comes back online if cloud checks are still allowed then.

### What opens a cloud call

Each call above starts only when all three hold, checked right before it:

- **Consent, on this device.** Each device asks its own question and keeps its own answer, in this browser's storage (`src/data/deviceConsent.ts`); Firestore holds no consent, and the rules refuse it on a box. The answer is read fresh right before each call, so a change made in another tab counts even before this page hears of it. Only "allowed" opens the cloud. Another tab hears a withdrawal as a storage event and aborts its work that has not been sent. The limit: a request already sent finishes, since a withdrawal cannot recall it. The Chrome extension's panel asks its own question and keeps the answer in the extension's storage (`extension/src/panel/Panel.tsx`): the bridge opens only after a yes, and a no closes it before the answer is saved.
- **The pause (`kill_cloud`).** Cloud checks stay off until Remote Config has given this browser a value of its own. If nothing was ever fetched and activated (a first visit with Remote Config blocked or offline), they stay off for the visit. A value fetched and activated earlier is used until the next successful fetch or real-time update replaces it. That is how Remote Config delivers settings, and it is the accepted limit: a new pause reaches a browser on its next fetch or update, not before.
- **This page.** The page is open, online, and not withdrawn; leaving the page aborts its calls.

### The service worker

`src/pwa/sw.ts`, written for this app. It caches only the app's own files (the page, its built code with the rules, fonts, icons and the web app manifest), never a reply from a Google host, and opens the cached page only for the app's own routes, matched on the path as the hosting matches them. It keeps the version before it, so a tab still on the old app keeps loading its files after another tab switched. Its kill switch: set the repository variable `BYT_SW_KILL` to `1` and run the deploy (`gh variable set BYT_SW_KILL --body 1`, then `gh workflow run deploy-live.yml`). Every deploy then ships the same worker with no files to cache, which waits while it deletes every cache, unregisters itself, then reloads each open tab once, until the variable is removed (`gh variable delete BYT_SW_KILL`) and the next deploy runs. A variable, not a commit, so a merge during an incident never brings the worker back. `tests/e2e/sw-kill.local.spec.ts` builds that worker and checks it removes an installed one.

### What Firestore keeps

A box and its items, for its members only. Never label text, never consent, and never an item's own name: each item carries the label of its category (for example "Perfume or cologne"), and the model's name or the sender's own words for it stay on the device (`src/data/deviceNames.ts`).
